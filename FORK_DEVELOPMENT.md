# Fork development rules

These rules apply to `deniszagitov/anarlog`, forked from `fastrepl/anarlog`. Follow the root and nearest component `AGENTS.md`, [CONTRIBUTING.md](CONTRIBUTING.md), and [LICENSING.md](LICENSING.md). Keep this document and the root pointer in a dedicated fork commit. No workflow guarantees conflict-free updates or upstream acceptance; the goal is a small, reviewable difference from upstream.

## Branches and change ownership

- `origin` is the user's fork; `upstream` is `https://github.com/fastrepl/anarlog.git`. Inspect existing URLs before configuring either remote. Never replace a remote silently or push directly to upstream.
- Keep `main` as the canonical default branch containing the compatible fork changes. Use the primary checkout for the application and retain `upstream/main` as the upstream reference. Temporary topic branches use `fix/`, `chore/`, or `refactor/`; additional worktrees are temporary and must not become separate maintained applications.
- Keep reusable changes and personal policy in separate commits. General bug fixes, provider compatibility, or an export extension can be proposed upstream. Branding, private paths, deployment settings, local feature eligibility, and these fork rules belong only in the fork.
- Build upstream contributions from a fresh `upstream/main` branch and cherry-pick only the relevant general-purpose commits. Do not open an upstream contribution from the fork’s `main`, which includes all customizations.
- Merge updates into published/shared branches. Rebase only unpublished work owned by this task. Do not force-push, rewrite shared history, discard changes, or alter another agent's work without explicit authorization. Never resolve an upstream merge by accepting all of one side.
- Check `git symbolic-ref --quiet --short HEAD` before version-control work. Use GitButler only on the literal `gitbutler/workspace` branch; these ordinary Git recipes apply to other branches. Do not switch branches to activate GitButler.
- Local edits and read-only investigation do not authorize publishing, releases, deployments, external messages, or tracker writes. Follow the authorization for the actual task. Upstream Linear links and release credentials are maintainer context, not evidence that the fork owner has access; continue locally if unavailable, as the workflow skill permits.

## Receive upstream updates

Run these steps only as part of an update task, after the current work is saved and `git status --short` is empty. Review licenses, migrations, release/build configuration, and provider/auth changes before merging. Inspect existing remote URLs before adding `upstream`; never replace a remote silently.

```bash
git fetch upstream
git log --oneline main..upstream/main
git log --oneline upstream/main..main
git diff --stat main...upstream/main
```

Preserve the fork history and merge into the canonical branch. Choose a unique backup branch name:

```bash
git switch main
git branch chore/fork-before-update-YYYYMMDD
git merge --no-commit upstream/main
```

A fast-forward may complete immediately even with `--no-commit`. Otherwise inspect the merge, resolve understood conflicts, run the relevant checks, and commit it. Stop for input on ambiguous behavior, data compatibility, or changes owned by someone else. Never reset `main` to an upstream mirror or force-push it. The backup branch preserves the previous fork tip. Publishing still requires authorization for the actual task.

After each update, inspect the complete remaining fork diff, remove patches already implemented upstream, and recheck the capability findings below. A source merge does not update an installed binary. Test the custom build with disposable data before using it with existing notes.

## Make changes that stay easy to merge

- Prefer configuration and supported provider interfaces before modifying core behavior. Desktop endpoint configuration is in [env.ts](apps/desktop/src/env.ts); local/BYOK provider definitions live under `settings/ai`. Keep credentials in ignored environment files or the existing secure settings flow. `VITE_*` values are embedded in the frontend: never put server secrets there.
- Prefer the existing CLI/MCP export surface or a small independent exporter for personal Obsidian processing. If the change belongs inside desktop, extend the existing [automation runner](apps/desktop/src/automations/engine.ts) and [Markdown export](apps/desktop/src/automations/markdown-export.ts) instead of duplicating meeting-completion orchestration. Keep personal vault paths and templates out of public commits. Export remains one-way unless an import contract is separately designed and tested.
- Use the [plugin SDK](packages/plugin-sdk/src/index.ts) only when its actual view/event interfaces cover the requirement; it is not an assumed arbitrary backend extension API. Renderer plugins run on the UI thread, so keep work bounded and follow [plugin runtime instructions](examples/plugins/AGENTS.md).
- Keep any local eligibility customization in one narrow, explicit capability policy with existing behavior as the upstream default. Do not globally set `isPro`/`isPaid`, fabricate account claims, or weaken hosted auth to enable a local action. Keep the general extension mechanism and the fork's enabling policy in separate commits.
- Preserve module ownership: schema in `crates/db-app`, database initialization in `db-core`, migrations in `db-migrate`, transports in `plugins/db`/`mobile-bridge`, and the Drizzle adapter in `packages/db`. Reuse existing hooks and transports; do not create a parallel TypeScript schema or database implementation.
- Keep shipped migrations append-only and downgrade-safe; follow [db-app rules](crates/db-app/AGENTS.md). Do not silently renumber an applied fork migration when upstream uses the same ID. Reconcile migration history and test fresh initialization plus upgrades before merging. Prefer existing settings or an independent store for purely personal data when that avoids changing shared/synced schema. Never add a table to CloudSync policy automatically.
- Follow the current React state, query, form, and effect conventions. Use existing abstractions; avoid unrelated refactors, mass formatting, generated-file edits, or dependency upgrades in a functional change. Use the owning generator for bindings, i18n, OpenAPI, and native bridges.
- Read the current `packageManager`, Rust toolchain, and workflows after syncing. Use their pinned versions and frozen lockfiles. Do not mix old setup notes or formatter versions with a new upstream revision.
- For distributable custom builds, use an explicit fork build configuration and a separate app identifier/storage location after checking native entitlements and paths. Review [stable updater configuration](apps/desktop/src-tauri/tauri.conf.stable.json) and its platform overrides: upstream update URLs can replace a custom binary with an official build. Configure the fork's update channel or disable it intentionally, and verify the resulting artifact. Keep signing keys, telemetry destinations, backend URLs, and release infrastructure under the fork owner's control. Do not edit upstream release defaults just to build a personal variant.
- Ad hoc macOS rebuilds change the executable identity used by Keychain and privacy checks. Verify access on the installed candidate; old approvals may need renewal. If Accessibility remains denied after a grant and restart, stop the fork and reset only its stale entry with `tccutil reset Accessibility so.anarlog.local-ai`, then add the exact installed bundle again and verify the running app. Do not reset permissions for every app. When a system prompt needs manual input, finish the intended candidate first and batch the required confirmations. Keep provider tokens in the secure settings flow instead of weakening Keychain access or adding plaintext fallbacks.

## Prepare an upstream contribution

1. Search public issues and PRs for an existing fix or maintainer direction. Discuss large interface, schema, or product changes before implementing them. A personal feature becoming useful does not imply maintainers want its default policy.
2. Start from a freshly fetched upstream base. When another checkout contains active work, use an isolated worktree rather than moving it:

   ```bash
   git fetch upstream
   git worktree add -b fix/descriptive-topic ../anarlog-upstream-change upstream/main
   ```

   Choose a new path and branch. Cherry-pick only the reusable commits there, including their regression coverage; inspect the full diff against `upstream/main` before publication. Exclude fork rules, unlock policy, personal integrations/configuration, unrelated cleanup, and private data.
3. For a feature, provide an independently useful default behavior, a small interface, and backward compatibility. For an Obsidian/export improvement, propose a configurable export capability with synthetic fixtures; keep the user's vault layout and local eligibility separate. Changing upstream monetization needs an explicit maintainer decision.
4. Follow the current [PR template](.github/PULL_REQUEST_TEMPLATE.md) and [description validator](.github/workflows/pr-description.yml). The external-contributor gate requires a specific title (at least 12 characters and three words), `## Summary` with a visible `**Intent:**` of 20–400 characters, and `## Demo` with a video/GIF URL or `N/A` plus a one-line reason for a nonfunctional change. Include `## Verification` with actual commands/results. Write the title and description for a maintainer who has not read this chat.
5. Format changed content and run the affected consumers' checks specified in the current workflows and root `AGENTS.md`. Root Markdown files currently fall outside the Markdown associations in `dprint.json`; `--allow-no-files` does not validate them. For a new root document, use a temporary formatter configuration with the same Markdown plugin version; preserve unrelated existing formatting in inherited files. Docs-only contributions still run the common CI checks. Do not add tests for prose; use [.agents/skills/testing/SKILL.md](.agents/skills/testing/SKILL.md) for behavioral changes. One regression test should catch the fixed behavior, not mirror its implementation.
6. Before proposing a contribution, run both license-boundary Python commands and the complete Node test invocation in [ci.yaml](.github/workflows/ci.yaml), plus the workflow security scan in [zizmor.yaml](.github/workflows/zizmor.yaml). Inspect findings; a successful scan process is not a clean security result. Report unavailable or unrelated failing checks explicitly. A skipped native job is not proof of platform support.
7. Preserve MIT and third-party notices/provenance. Keep community code independent of `enterprise/**`. Enterprise contributions require Fastrepl's written terms. See [licensing](LICENSING.md) and [CODEOWNERS](.github/CODEOWNERS).
8. Push to `origin` and open a PR targeting `fastrepl/anarlog:main` only when the user asks. Passing CI makes a contribution reviewable; maintainers decide acceptance. After an upstream squash merge, remove the equivalent fork patch using its actual resulting diff rather than assuming the commit SHA stayed the same.

## Self-built capabilities and licensing

Code snapshot: `2a40e41654a4635550ead51af23137608bd8422d`, inspected on 2026-10-22. These findings describe this checkout; recheck changed gates and licenses after upstream updates. No application build, account entitlement, or hosted-service behavior was verified in this audit.

Building the existing source does **not** automatically enable Pro. The client derives `isPro` and `isPaid` from account claims, including trial expiry and paused subscriptions ([billing derivation, lines 22–59](packages/supabase/src/billing.ts#L22-L59)). MIT permits modifying community code while retaining its required notices; that includes the local product policy. Server authentication verifies JWT signatures using the configured Supabase JWKS and checks entitlements from the verified claims ([token verification, lines 44–59](crates/supabase-auth/src/server/mod.rs#L44-L59), [entitlement checks, lines 114–143](crates/supabase-auth/src/server/mod.rs#L114-L143)). A local UI flag cannot change those claims. Keep hosted billing/auth checks intact and never make the global billing provider pretend the user has a subscription just to expose a local feature.

The community API and Supabase definitions are available to build an independently configured service under their applicable licenses. Running a desktop build is not a self-hosted deployment: auth, database migrations, storage/sync infrastructure, OAuth applications, integrations, and AI provider credentials must be configured and operated separately; relevant infrastructure and provider costs remain. Follow [CONTRIBUTING.md](CONTRIBUTING.md) and [API setup](apps/api/AGENTS.md). A turnkey self-hosted Pro stack was not established by this audit.

For this fork, prefer supported local/BYOK providers and independent local exporters first. If a local gate must change, introduce a narrow local capability policy and test the selected end-to-end behavior. Keep that fork policy change separate from improvements proposed upstream. Any proposal to change upstream packaging or Pro eligibility needs a maintainer decision; technical feasibility does not imply acceptance.
